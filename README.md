# Workbench

A local triage board for Claude Code sessions. Answers: *what am I in the middle of,
what's unfinished, what can I drop* — and lets you resume any of it in one click.

    wb                 # open the UI
    wb index           # rebuild the session index
    wb stop / restart / log

## Always on

A LaunchAgent (`~/Library/LaunchAgents/ai.reachthepeople.workbench.plist`) starts the
server at login and restarts it if it dies. It runs `bin/serve`, which resolves node at
runtime rather than baking in a path, so an `nvm install` will not break it.

    launchctl list | grep workbench            # is it up
    launchctl unload|load ~/Library/LaunchAgents/ai.reachthepeople.workbench.plist

### Friendly hostname

    http://claude.localhost:7788

Nothing to install. Any `*.localhost` name is reserved by RFC 6761, resolves to
loopback with no `/etc/hosts` entry, and Chrome treats it as a **secure context**, so
`navigator.clipboard` works. Any prefix does — `wb.localhost` too.

Two dead ends, both measured rather than assumed:

| Approach | Why it fails |
|---|---|
| `claude.local` in `/etc/hosts` | `.local` is reserved for mDNS. macOS resolves it by multicast, so `curl` stalls ~4s and fails regardless of `/etc/hosts`. Measured: `.local` 4020ms/fail vs `.localhost` 17ms/200. |
| pf `rdr` :80 → :7788 | Does not apply to locally-originated loopback traffic. With the anchor loaded, `127.0.0.1:80` was still refused. |

### Dropping the port

    sudo ~/.claude/workbench/bin/install-port80     # -> http://claude.localhost
    sudo ~/.claude/workbench/bin/install-port80 --undo

Port 80 needs a privileged bind, but the workbench must never be root — it spawns
interactive shells. So launchd does the privileged part and nothing else: it binds
:80 (v4 and v6), then hands each accepted connection to `/usr/bin/nc` running as
**you**, which pipes it to 127.0.0.1:7788. Root owns a listening socket; it never
owns a process that can run your code.

Verified on a scratch port before shipping: HTTP 200 in 28ms through the relay, the
`Host` header arriving intact (so `evil.example` still gets 403), and the terminal
WebSocket staying open with keystrokes round-tripping.

The Host allowlist accepts loopback and `*.localhost` only; `evil.localhost.attacker.com`
and anything else gets 403. If an earlier version put `claude.local` in your hosts file
plus a pf anchor, remove it with:

    sudo ~/.claude/workbench/bin/setup-hostname --undo

## Starting new work

**＋ New session** (board header, or the work rail) mints a UUID, passes it to
`claude --session-id`, opens a tmux session in the directory you pick, and drops you
into the terminal. Because the id is assigned up front, the tmux session, the terminal
tab and the transcript that appears later all share one identity — no reconciliation.

The directory list is ranked by how often you actually work there, derived from the
index; you can also type any path.

The name you type is saved as the item's title the moment the session is created, so it
survives before the transcript exists — and it outranks whatever the session later calls
itself. Leave it blank and the row inherits the session's own title instead.

## Naming and renaming

Titles resolve in this order, most specific first:

    item.title       typed in the workbench — ⋯ › Rename…
    custom-title     typed in the session — `claude --name`, /rename
    ai-title         generated by Claude Code
    first prompt     first 80 characters

Renaming anywhere shows up everywhere: the rail and the work header re-read their title
from the board on every refresh rather than keeping the name a tab was opened with.

## Model

Three layers, coarse to fine:

    Initiative   a theme or workstream — "Revenue Intelligence", "Proposals & Collateral".
                 NOT a repo. Rename, recolour, archive, or add your own.
      Item       a piece of work. Owns one or more sessions (merge duplicates).
        Session  one Claude Code conversation.

An item's initiative is either **assigned** (you moved it) or **auto-grouped** by the
weighted keyword rules in `data/initiatives.json`. Assignment always wins; the drawer
shows "auto-grouped" when the classifier picked it. ~87% of history classifies
automatically — the rest lands in **Unsorted** for you to place.

Editing an initiative's rules is how you teach it; rules are data, not code.

Storage, deliberately separated:

| Layer | Source | Rebuildable |
|---|---|---|
| Derived | `~/.claude/projects/**/*.jsonl` — title, project, branch, prompts, activity | yes, always |
| Overlay | `data/items.json` — status, priority, assignee, tags, note, Jira key, initiative | **no — this is the only real data** |
| Taxonomy | `data/initiatives.json` — initiative names, colours, matching rules | hand-authored; back it up |

Every overlay write snapshots the previous file into `data/backups/` (last 50 kept).
The index is a cache; delete it and `wb index` rebuilds it.

Titles come from Claude Code's own `ai-title` records — nothing is generated here.

## Copying text out

The Claude TUI turns on mouse tracking (`mouseTrackingMode: drag`), so a plain drag is
delivered to the app instead of selecting text. That is the app's behaviour, not a bug
in the terminal.

- **⌥ drag** selects locally (`macOptionClickForcesSelection`), then **⌘C** copies.
- **⧉ Copy** in the work header reads the text straight out of tmux — selection,
  visible screen, last 1,000 lines, or full scrollback. This is the dependable route:
  it ignores mouse mode entirely and reaches real scrollback, which a browser
  selection cannot.

### Shift+Enter

xterm.js sends a bare CR for Enter no matter which modifiers are held, which the TUI
reads as "submit". Shift+Enter (and ⌥Enter) instead send `ESC CR` — the same sequence
`claude /terminal-setup` installs in real terminals. The handler must `preventDefault()`:
returning `false` only stops xterm, and the keypress that follows would still deliver a
CR and submit the line anyway.

### Dropping a file in

Drag a file onto the terminal and its **path** is pasted, as iTerm does. The browser
never exposes a dropped file's path, so it is recovered rather than read:

1. a text drag (`text/uri-list`, a `file://` URL) already carries the path — used as is;
2. otherwise Spotlight is asked for that filename, and a hit only counts if size and
   mtime also match. Two identical candidates resolve to nothing rather than a coin flip;
3. nothing matched — dragged out of another browser, an unindexed volume — so the bytes
   are written to `data/drops/` and that path is pasted. What lands in the prompt always
   points at something readable.

The path goes in as a bracketed paste, so the TUI sees one paste and not a burst of keys.

Clipboard writes fall back to `execCommand` when `navigator.clipboard` is unavailable,
which is the case over `http://claude.local` — a non-secure origin.

## Closing a session

There are three different things "close" can mean, and they are deliberately separate:

| Action | Where | What it does |
|---|---|---|
| **End** | ✕ in the work rail or on a dock tab | Kills the tmux session. Asks first if a turn is in flight. The conversation is not lost — resume it from the board. |
| **Detach** | ⌥-click the same ✕ | Closes the browser view only. claude keeps running; the row keeps its live dot. |
| **Wrap up** | ✓ in the work rail, or ⋯ → Wrap up on a row | Asks where the work landed, then optionally ends the tmux session too. |
| **Exit from inside** | `/exit` in the TUI | Ends claude. The tmux container stays behind holding a shell. |

✕ ends rather than detaches because every session is resumable: an abandoned tmux
container is pure clutter, while the only thing a kill actually destroys is a turn
that is still running. So that is the one case it stops to ask about, and it is the
only thing `/api/session/status` exists to detect — the TUI prints `esc to interrupt`
in its footer for exactly as long as it is working, and the process tree looks
identical either way, so the pane text is the only place that knows.

That last case is why the rail shows **"N finished — clear"**: a tmux session outliving
its claude process is normal, and `listLive()` only counts sessions whose pane is
running something other than a shell — otherwise the board would show a live dot for
work that already ended. Clearing removes the empty containers.

A session started from **＋ New session** that never receives a prompt has no
transcript, so it has no row on the board. It still shows in the work rail while its
tab is open, and in "N finished — clear" once you exit it.

Status is only ever set by a person. The workbench never guesses it.

- **Wrap up (✓)** in the work rail — pick where it landed, add an optional note, and
  optionally end the tmux session. One click at the moment you actually know.
- If you exit `claude` anywhere else, a `SessionEnd` hook flags the item and it lands
  in **Needs wrap-up**, so nothing is silently lost. `/clear` is not a close and does
  not flag. Setting a status anywhere clears the flag.

### Why not infer it

Measured over the real corpus: **96% of sessions end on an assistant message** (536 of
559), interruption markers appear in 1 of 60 transcripts, and of the 40 most recent
sessions only 2 ended asking a question and 8 claimed completion — **30 gave no signal
at all**. Endings are indistinguishable: Claude finished a thought and you walked away.

An inferred "done" would therefore be mostly a confident guess, and wrong in the
dangerous direction — it hides live work, which is the exact failure this tool exists
to prevent. So staleness is inferred; status is asked.

## Statuses / priority

`Not started → Working on it → Paused → Stuck → Done → Dropped`, crossed with
`Now / Next / Someday`. `Dropped` matters most: a list you can't kill items on stops
being usable.

## Two modes

**Board** — planning. Initiatives, statuses, owners, the whole picture.

**Work** — doing. The board gets out of the way: a rail of open sessions on the left,
the TUI takes everything else. On a 939px-tall window that is 49 terminal rows versus
18 in the docked view.

- `⌥Tab` toggles, and works even while the terminal has focus (xterm never sees it).
  The header button does the same.
- Clicking ▶ on a row switches to Work automatically and opens the session.
- The Work rail has two lists: **Open sessions** (click to switch, ✕ to end, ⌥✕ to detach) and
  **Start a session** — a filterable list of everything still open, so you can begin
  the next one without going back to the board.
- Terminals stay alive across mode switches; in Board mode they return to the bottom
  dock so you can watch a run while you plan.

### Reading the rail at a glance

Each open session carries a dot saying what its agent is doing right now. Three
shapes rather than three shades, so it survives a glance:

| | | |
|---|---|---|
| ● filled green, breathing | **Working** | a turn is in flight — leave it alone |
| ○ green ring | **Waiting for you** | claude is up and idle at the prompt |
| ● flat grey | **Stopped** | claude exited; the pane is a shell, or the socket dropped |

Sessions in **Start a session** get the board's live pulse when claude is running in
them somewhere else — an iTerm attach, say — so a busy session is never invisible
here just because its terminal is not open in the app.

The working/waiting split is read straight off the terminal the tab already holds:
the TUI keeps `esc to interrupt` in its footer for exactly as long as it is working,
so an open tab knows without asking the server, and the dot repaints on a 1.2s tick
instead of going stale until the next 30s board refresh.

## Working in the UI

- Sidebar filters by initiative or view (All / Unsorted / Unassigned).
- **Open** shows live work; **Everything** includes Done and Dropped.
- Click a status or priority cell to change it; click the avatar to assign.
- Select rows for the bulk bar: move to initiative, set status, merge duplicates.
- `⋯` on a row moves it; `⋯` on a group recolours or archives the initiative.
- Click a group name to rename it inline. `/` focuses search, `Esc` clears.

### Theme

The glyph in the sidebar footer cycles four stops, and its shape names the one
you are on:

| | | |
|---|---|---|
| ◐ | Follow system | tracks `prefers-color-scheme` |
| ● | Dark | app and terminal both dark |
| ○ | Light | app and terminal both light |
| ◑ | Light app, dark terminal | the board stays light, the pane goes dark |

The last one exists because the two surfaces don't have to agree — a TUI reads
better on a dark pane even when nothing else does. The dock's box follows the
terminal rather than the page (`--term-bg`, published from xterm's own palette),
so a dark pane never sits inside a bright frame.

## Automated sessions

Cron and SDK runs (`entrypoint: sdk-cli`) are **excluded from the board entirely**.
A machine execution has no status to triage, and tracking them would mint a new
overlay row per run, forever.

They are still indexed, so this is reversible with no data loss:

    WORKBENCH_INCLUDE_AUTOMATED=1 wb restart

That surfaces them again (762 rows as of writing, mostly Lookout triage and
production health reports). What they produce is tracked in the Lookout issue
tracker, not here.

## Resume — in the browser or in iTerm

tmux is the durable layer; everything else is just a viewport onto it. A session is
`wb_<8-char session id>`, cd'd to the session's original cwd, running `claude --resume`.

- **▶ on a row** opens a real terminal in the app, docked at the bottom. Multiple
  tabs, drag the top edge to resize, `⤢` to maximise.
- **⋯ → Open in iTerm** attaches an iTerm tab to the *same* tmux session instead.
- Both can be attached at once. `window-size latest` means whichever client is
  active drives the geometry, so they swap freely.
- Closing a terminal tab **ends** the session; ⌥-click detaches instead, leaving it
  running with its live dot for iTerm to pick up.
- **Fork into terminal** does the same with `--fork-session`.

### How the terminal works

No native modules. `lib/ptyhost.py` allocates a PTY with `forkpty()` and relays it
over stdin/stdout, with resizes on fd 3 (macOS `script(1)` refuses to run unless its
own stdin is a TTY, which rules it out here). `lib/terminal.js` bridges that to a
WebSocket; the browser renders with a vendored xterm.js in `public/vendor/`.

`ws` is the single runtime dependency. If it is missing the board still works and the
terminal is simply disabled — the server says so at startup.

Sessions created for the dock get `status off` (the dock shows the name and cwd) and
`history-limit 50000`.

## Auto-capture

A `Stop` hook (`hooks/session-stop.js`, registered in `~/.claude/settings.json`)
indexes each session as it ends and files it under `inbox`. It exits 0 on every
path — it can never fail a session.

## Layout

    lib/indexer.js   incremental transcript scan -> data/index.json
    lib/store.js     the overlay: items, merge, backups
    lib/view.js      joins the two into rows; untracked sessions show as virtual items
    lib/launch.js    tmux + iTerm
    server.js        loopback-only HTTP + JSON API
    public/          the UI

## Notes

- The server binds to `127.0.0.1` and rejects non-local Host and cross-origin POSTs.
  The WebSocket upgrade additionally refuses any path but `/ws/term` and any
  non-loopback Host or Origin. **This endpoint hands out an interactive shell** —
  never bind it to a public interface or put it behind a proxy.
- Port via `WORKBENCH_PORT` (default 7788).
- Narrow-viewport layout (`max-width: 860px`) is written but has not been verified
  in a browser.
